# Reflection Report

### What challenges did you face during the schema refactor?
The primary challenge during the schema refactor was balancing the need to handle massive transactional write loads (thousands of transactions per second) with the requirement to serve large-scale analytical queries. In a traditional normalized database, querying sales trends across millions of order records would cause significant performance bottlenecks and lock contention. In NoSQL, deciding which fields to denormalize without creating data inconsistency requires careful consideration. Ensuring partition tolerance while maintaining acceptable consistency levels under high load was also a key architectural challenge.

### How did the new requirements affect your design decisions?
The new requirements—analytics and high availability—pushed the design towards aggressive denormalization and sharding. To satisfy the analytics requirement, I introduced a `total_sales_count` and `total_revenue` on the `Products` collection and added a `category` field to the embedded order items. I also introduced a pre-aggregated `monthly_sales_analytics` collection, avoiding the need for heavy on-the-fly computational aggregation during reads. For high availability and partition tolerance, I adopted a sharded cluster model. Data is distributed across shards based on carefully chosen shard keys (e.g., `category` for products and `created_at` for orders), and each shard uses a primary-secondary replica set to ensure the system remains available even if nodes fail.

### How did the refactor improve the system in terms of scalability, availability, and query performance?
The refactored design dramatically improves **scalability** by partitioning collections across multiple nodes, ensuring that neither storage nor write throughput is limited to a single machine. **Availability** is enhanced via replica sets, providing automatic failover and data redundancy, keeping the application online despite hardware failures. Finally, **query performance** for analytics is significantly boosted because complex JOIN-like operations and full table scans are replaced by reading pre-aggregated documents and utilizing denormalized fields, yielding near-instantaneous responses for sales trends.
